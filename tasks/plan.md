# ATK YOGO 75 PRO 功能可行性与实施计划

## 目标与结论

开发面向当前 macOS 的原生可视化应用，让用户在应用内切换编程模式和电量模式；键盘点阵屏显示 Codex、ZCode 全部会话的聚合状态或键盘电量。右侧两枚可编程按键分别用于启动 Codex、ZCode 或切换至已启动的对应应用。首期支持 2.4G 和有线连接，不要求蓝牙。项目尚无实现代码；本计划不涉及实施。2026-11-13 本机 USB 设备树中识别到 `ATK YOGO 75 PRO Dongle`，说明接收器已连接，但未证明键盘在线或可以通过该链路写屏；本机存在 `/Applications/ZCode.app`。

| 能力 | 初步判断 | 主要前提 |
| --- | --- | --- |
| 实时显示任务状态 | 有条件可行，中等风险 | 实机确认当前固件及连接方式可写屏；找到可靠的桌面会话状态来源 |
| 显示键盘电量 | 原生显示可行；自定义模式尚待验证 | 官方说明书提供电量显示；持续显示、精确百分比和主机读取能力需要验证 |
| 快捷键启动或切换应用 | 高可行性 | 确认可编程键可发送可识别且不冲突的按键，以及应用激活行为 |

官方说明书列出像素屏显示当前电量和右侧控制自定义功能；它没有保证屏幕可由第三方实时写入或提供电量读取接口。[说明书](https://manuals.plus/m/97c70dcbfc2a251e4cd0748d21a7238e5ccda103e1544456b4c1c6d2698bab97)。ATK 已公布点阵屏自定义动画能力，但静态配置或动画不等于外部实时控制。[ATK 更新说明](https://bbs.atkgear.com/article/2806)。第三方项目 [rossgpt/yogo](https://github.com/rossgpt/yogo) 声称通过 USB HID 驱动 6×6 点阵屏；其固件、平台、2.4G 和许可证兼容性都需核实，不视为本机实测结论。

## 能力划分及依赖

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| device | 识别设备、连接、读电量和写屏 | 无 |
| status | 分别采集并聚合 Codex、ZCode 会话状态 | 具体应用可用的事件接口 |
| display | 模式、6×6 图案、刷新及状态失效处理 | device、status |
| launcher | 识别快捷键并启动或激活应用 | 可编程键配置、macOS |
| app-ui | 原生可视化界面、模式切换与运行状态展示 | display、device、status、launcher |

建议先分别验证 device、status、launcher，再实现 display 和 app-ui；launcher 可先独立验证。

## 技术方案与边界

1. **设备层**：优先验证当前 2.4G 接收器的 HID 接口，再验证有线。先查阅现有协议和许可证，以最小、可恢复的测试画面验证。不修改固件、不执行恢复出厂设置；备份已有屏幕配置，测试结束恢复。确定写入是否持久化、是否涉及闪存后才决定刷新频率。ATK HUB 与第三方程序同时运行时的冲突也需检查。
2. **状态层**：分别为 Codex 和 ZCode 实现适配器，只传应用、会话标识、状态及时间戳，不传提示词或代码。Codex 官方 app-server 描述了会话状态变化和等待批准标记，但这只证明该协议有状态，并不证明可以无侵入地订阅现有桌面应用进程；需要实测现有桌面会话、CLI 和多会话覆盖。`notify` 文档目前只保证轮次完成事件，不能单独覆盖全部状态。[Codex app-server](https://learn.chatgpt.com/docs/app-server)；[Codex 通知](https://learn.chatgpt.com/docs/config-file/config-advanced)。ZCode 官方文档提供 Hooks，但应逐项验证本机桌面版是否触发、事件能否覆盖等待确认和恢复。[ZCode Hooks](https://zcode.network/cn/docs/hooks/)。不可靠或过期的状态显示为未知，不伪装为完成。
3. **显示层**：建议在 6×6 屏左右各占 3 列，分别代表 Codex 和 ZCode，通过颜色加不同点阵/闪烁区分状态；实机先确定辨识度。待确认包括权限审批和需要用户回答的问题。建议状态优先级为待确认 > 进行中 > 已完成；没有活动会话或事件来源失效时显示空闲/未知。多个会话按应用聚合，同一应用有多个状态时采用上述优先级；失败、中断和超时单独显示为异常/未知，不归为完成。完成状态保留时间与是否自动清除待确认。
4. **电量模式**：在 6×6 屏幕上使用居中的 4×5 电池图标，以 100%、80%、60%、40%、20% 五档图案和颜色梯度显示电量，而非显示数字百分比。建议将有效读数按 81–100%、61–80%、41–60%、21–40%、1–20% 映射到对应档位，0% 和无法读取均单独处理，不误报为 20%；档位和颜色需在真机上验证辨识度。先验证能否稳定读取电量；若只能使用原生快捷键，则将原生电量显示作为降级方案，并明确该方案不满足自定义五档图标的完整要求。不可读取时不估算电量。
5. **快捷键**：右侧两枚实体键分别用于 Codex 和 ZCode，核心功能是启动对应应用，或将已启动的应用切换至前台。优先用 ATK HUB 将其映射到不冲突的组合键，由原生应用识别；按应用 bundle ID 找到运行实例并激活，未运行时启动。必要时考虑系统辅助功能权限；确认最小化窗口、多个窗口和多个桌面空间的行为。应用路径、bundle ID 和映射按键在实测阶段确定。
6. **原生应用和运行方式**：以 macOS 原生可视化应用为交付对象，技术方案优先评估 Swift、SwiftUI 和系统原生接口，具体版本及 HID 库由原型验证决定。界面至少提供编程/电量模式切换、连接状态、当前显示预览及所需权限提示；切换后即时应用到已连接键盘。先手动启动原型，稳定后再评估登录启动、安装和卸载。设备断开、休眠唤醒、模式切换、进程重启时自动恢复，状态过期则显示未知。

## 阶段与决策点

任务清单、依赖和验收见 [todo.md](todo.md)。

- **阶段 0：边界确认与原型验证，约 0.5–2 天。** 检查固件、屏幕、HID、状态事件和按键映射；产出兼容性矩阵。优先验证 2.4G，必要时比较有线。若不能安全写屏，停止实时显示路线，保留原生电量和快捷键独立方案。
- **阶段 1：独立快捷键，约 0.5–1 天。** 实现两个应用的启动与切换，完成实际按键验收。
- **阶段 2：屏幕、原生界面与电量闭环，约 1–3 天。** 做最小图案、原生可视化模式切换及可用电量路径，测试断连恢复和官方配置恢复；原生界面工作量依验证结果调整。
- **阶段 3：状态闭环，约 1–4 天。** 分别接入 Codex 与 ZCode，覆盖各自可验证的事件，并对不可用状态诚实降级。
- **阶段 4：稳定性与交付，约 0.5–2 天。** 整体验收，记录安装、权限、故障排查及撤销方法。

以上为粗略开发人日，合计约 3.5–12 人日，不含等待硬件、协议逆向失败或厂商支持的时间。阶段之间以验收结果决定继续；屏幕和状态的未知项可能使完整需求不可达。

## 主要风险与替代

| 风险 | 应对 |
| --- | --- |
| 2.4G 不暴露写屏通道或固件协议不兼容 | 验证有线；仍不可用时停止实时显示，不猜测或刷写固件 |
| 写屏命令持久化、设备控制冲突 | 先审查协议及现有实现，低频测试并备份/恢复配置 |
| 桌面版状态接口不可旁路订阅 | 先采用受支持 Hooks/通知；仅覆盖有可靠事件的会话，未覆盖者显示未知 |
| 审批之后缺少恢复事件或程序崩溃 | 每会话状态机、启动重建和过期时间，缺证据即未知 |
| 屏幕太小、颜色不易区分 | 图案与颜色共同编码，实机确认后调整；必要时轮显 |
| 多设备连接时事件指向错误电脑 | 明确每个主机独立运行及连接归属，切换设备时重新同步 |

## 需要确认的产品选择

- 编程模式与电量模式是否需要在应用内手动切换之外支持自动切换？
- 五档颜色的具体配色、边界值及 0% 图案是否采用上述建议，待真机辨识度验证后确定。
- “完成”指最近一轮完成还是整个任务完成？保留多久？多个窗口时需要切换到哪个窗口？

上述问题不阻碍前期只读核查和低风险原型设计，但会影响最终验收。
